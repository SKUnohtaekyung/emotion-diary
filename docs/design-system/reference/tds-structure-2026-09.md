# TDS Mobile 문서 구조 관찰 (2026-09-26)

토스 TDS Mobile은 채택하지 않았다(D-039). 이 기록은 **"부품마다 어떤 종류의 결정을 문서화하는가"라는 구조만** 우리 문장으로 적은 것이다. 코드·CSS 값·수치·속성 이름·이미지·문구 원문은 옮기지 않았다. 출처는 https://tossmini-docs.toss.im/tds-mobile/ (확인일 2026-09-26).

**writer 표본 대조(2026-09-26)**: 페이지 원문과 3건 모두 일치 — 확인 대화상자는 버튼 문구가 길어지면 나란히에서 위아래로 바뀐다 / 숫자 증감 부품은 늘리기·줄이기 버튼마다 스크린리더 이름을 따로 둔다 / 스위치는 라벨을 부품 밖에서 붙이고 누름 반응을 끌 수 있다.

## 문서 구성

- 기초는 색과 글자 둘뿐이다. 간격·움직임은 따로 기초 절이 없다.
- 형태가 하나인 부품은 한 쪽짜리 문서, 형태가 여럿으로 갈리는 부품(대화상자·하단 고정 버튼·입력·목록 줄·약관 동의)은 "이해하기" 쪽과 "형태별 실전" 쪽으로 나눈다.

## 우리 틀에 반영한 결정 종류 (→ CHECKLIST)

| 관찰한 결정 종류 | 반영 |

| 버튼 로딩 중에 폭을 그대로 둔다 | §3 버튼(로딩 중 폭·다시 누르기) |

| 바텀시트가 높이 방식·닫는 법 세 가지·초점 가두기·큰 글자일 때 제목의 스크롤 포함 여부를 정한다 | §3 바텀시트 |
| 대화상자 버튼 문구가 길면 배치를 바꾼다, 바깥을 눌러 닫을지 정한다 | §3 확인 대화상자 |
| 토스트가 위치에 따라 동작 버튼 허용이 다르고, 스크린리더 알림 방식(끼어들기/차례 기다리기)을 고른다 | §3 토스트, §1 F9 |
| 입력의 라벨을 '늘 보임'과 '입력하면 나타남' 중에서 고른다 | §3 텍스트 입력 |
| 결과 화면이 그림 → 제목 → 설명 → 버튼 순서를 구조로 고정한다 | §3 빈 상태·결과 화면 |
| 스켈레톤이 실제 내용의 모양(제목 위치·아이콘 유무)을 닮게 조합을 둔다 | §3 진행·로딩 |
| 거의 모든 부품이 '역할·상태는 자동으로 읽히고, 목적이 애매한 곳(아이콘만 있는 버튼 등)은 설명을 직접 붙인다'는 같은 접근성 원칙을 반복한다 | §2 K항목 |

## 예상 밖 발견

- TDS의 'Stepper'는 숫자 증감이 아니라 **단계 진행 표시**이고, 숫자 증감은 다른 부품이 맡는다. 이름만 보고 대응시키면 틀린다 → 우리는 '증감 버튼'이라 부른다(CHECKLIST §3 강도 선택).
- 문서는 "어떻게 쓰나"에 집중하고 "왜 이렇게 정했나"는 거의 적지 않는다. 우리 부품 파일은 N항목에 근거(D-번호)를 반드시 적는다.
- 진행 막대 문서에 접근성 서술이 없다.

## 미확인

슬라이더의 범위(두 손잡이) 지원, 슬라이더·숫자 증감의 키보드 동작, 바텀시트 여러 개 겹치기, 앱인토스 디자인 가이드 전체 목차.
