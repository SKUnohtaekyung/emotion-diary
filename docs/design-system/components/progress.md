# 작성 흐름 진행 표시

기본 부품 · 틀은 [CHECKLIST.md](../CHECKLIST.md) · 상태 공통 규칙은 [DESIGN_SYSTEM §5.1](../../DESIGN_SYSTEM.md)(D-098, 이 부품은 상태가 하나뿐이라 대부분 해당 없음) · 측정 기준 시안 `1bfd066`

**상태: 결정 대기 0건**(2026-09-26 D-099로 2건을 위임 판단으로 정함 — 각 항목의 '정함'을 보라). 이 부품은 INVENTORY가 "없음(명세 절이 없다)"으로 표시한 부품이라 아래는 시안에서 새로 읽어 낸 값이다. 로딩 스켈레톤(뼈대 막대)은 다른 부품(`status-block`, 이 문서의 범위 밖)이다 — 아래 CHECKLIST §3 질문 중 스켈레톤 관련 항목은 "해당 없음"으로 답한다.

## A. 쓰임

- **쓸 때**: 작성 흐름(사건 → 마음 고르기 → 세부 감정 → 크기 → 이유 → 칭찬 → 감사 → 편지) 안에서 지금이 전체 몇 걸음 중 몇 번째인지 보여줄 때. 화면 맨 위, 뒤로가기·걸음 수 글자 줄 바로 아래.
- **쓰지 않을 때**: 데이터를 불러오는 동안의 기다림 표시(→ 상태 블록, 다른 부품) · 저장 중임을 알리는 것(→ 화면 상단 저장 상태 글자, §6.6) · 강도(크기) 값의 크고 작음(→ [강도 선택기](../../DESIGN_SYSTEM.md#64-강도-선택기-1~10), 전혀 다른 부품).

## B. 구조

`web/js/views/write.js:353`, `web/css/write.css:9-10`.

- `<div class="progress" role="progressbar">` 안에 채움 막대 하나(`<i>`, 인라인 `style="width:N%"`).
- 걸음 수 글자("N / M")는 이 부품이 아니라 위쪽 `.wf-count`(닫기·⋯메뉴와 한 줄)에 따로 있다 — 진행 막대 자신은 숫자를 보여주지 않는다.

## C. 변형

없음 — 화면마다 색만 달라질 뿐(M 참고) 구조는 하나다.

## D. 크기

- 높이 3px 고정, 반경 `radius.chip`(999, 알약 — 얇은 막대라 시각적으로는 그냥 둥근 끝처럼 보인다).
- 폭은 화면 좌우 여백 안에서 가득(`margin:0 0 space.3`, 좌우 별도 여백 없음 — 부모인 `.screen` 패딩을 그대로 받는다).
- 채움 폭은 `(at+1)/전체 걸음 수 * 100%` — 최소 폭 제한 없이 1걸음째부터 이미 부분 채움으로 시작한다(0%가 아님).

## E. 값

| 속성 | 값 |
| --- | --- |
| 트랙(빈 부분) | `border`(옅은 회색, 흰 화면 기준) |
| 채움 | `service-ink` |

**결정(D-099) E1 — 감정 색 면(계열 300) 위에서 트랙 색을 바꾸지 않는다**: 마음 고르기(`.screen.pick`) 화면은 진행 표시 트랙 배경을 초록 언덕에 맞춰 `color-mix(ink 14%, transparent)`로 따로 덮어쓴다(`write.css:38`). 그런데 **세부 감정 화면**(그 계열 300이 화면 전체를 물들이는 화면, §3.3 ①)에는 이런 덮어쓰기가 없어 트랙이 기본값(옅은 회색 `border`) 그대로 계열 색 위에 얹힌다 — 계열마다 대비가 다를 수 있다(예: 슬픔 300 위 옅은 회색은 상대적으로 잘 보이지만 기쁨 300 위에서는 흐려 보일 수 있다, 실측 안 함). 마음 고르기처럼 이 화면도 `[data-theme-cat] .progress`에 색 규칙을 추가할지, 지금처럼 두어도 채움(ink)만 보이면 충분하다고 볼지. *(추천: 추가한다 — 마음 고르기에서 이미 같은 이유로 트랙을 조정했고, 아홉 계열 모두에서 트랙 대비를 한 번에 검사(`check-contrast`)에 추가하는 편이 계열마다 따로 확인하는 것보다 안전하다.)* → **정함(D-099, 위임 판단)**: 맞춘다 — 트랙은 '바탕에서 만든 색'(바탕+ink 12%)으로 모든 바탕(흰·감정 300·언덕)에 같은 규칙을 쓴다. 채움은 ink.

## F. 상태

CHECKLIST §3 "진행·로딩" 질문에 답한다.

- **"진행률을 모를 때→알 때로만 바뀌고 거꾸로 가지 않는가"**: 해당 없음에 가깝다 — 이 진행 표시는 "모름→앎"으로 바뀌는 로딩형이 아니라 **처음부터 분모·분자를 아는 걸음 수 진행**이다(`role=progressbar`의 `aria-valuemin`/`max`/`now`가 항상 정해진 값). 다만 "이전" 버튼으로 뒤로 가면 채움이 **줄어든다**(`at`이 줄어드는 만큼 `width%`도 줄어듦) — 일반적인 단계형 진행 막대의 정상 동작이지 결함이 아니다.
- **"자리 표시(스켈레톤)는 실제 내용의 모양을 닮는가"**: 해당 없음 — 스켈레톤은 이 부품이 아니라 `status-block`(다른 부품)의 몫이다.
- **"로딩 문구를 읽어 주나"**: 아니다 — 단계가 바뀌면 포커스는 그 단계의 `<h1>`으로 이동할 뿐(`web/js/main.js:58` `main.querySelector("h1")?.focus()`) 진행 막대 자체에는 `aria-live`가 없어 "N / M" 변화가 스크린리더에 자동으로 읽히지 않는다. 스크린리더 사용자는 진행 막대에 직접 초점을 옮겨야 `aria-valuenow`를 듣는다.

| 상태 | 값 |
| --- | --- |
| 기본 | 위 E, 채움 폭은 매 단계 다시 계산 |
| 누름/초점/비활성/선택/로딩 | 해당 없음 — 이 부품은 누르거나 고르는 대상이 아니다 |

## G. 동작

- 다음/이전을 누르면 화면 전체가 다시 그려지며 진행 막대의 채움 폭도 함께 바뀐다(전환 애니메이션 없음 — 즉시 새 폭으로 그려짐, 아래 J).
- **분모(전체 걸음 수)가 고정이 아니다**: 걸음 목록은 `buildSteps()`가 그 시점의 `state.draft.cats`로 다시 계산한다(`write.js:43-49`) — 마음 고르기로 돌아가 계열을 더 고르거나 빼면 세부 감정 화면 수가 늘거나 줄어 **전체 걸음 수(분모) 자체가 달라진다**.

**결정(D-099) G1 — 되돌아가 계열을 바꾸면 분모가 바뀐다**: 예를 들어 계열을 2개 골라 8걸음이던 진행이, 마음 고르기로 돌아가 계열을 4개로 늘리면 다음에 다시 계산될 때 10걸음으로 늘어난다 — 사용자 눈에는 "진행이 갑자기 줄어든 것처럼"(같은 위치인데 분모가 커져 퍼센트가 작아짐) 보일 수 있다. 처음 진입 시점의 총 걸음 수를 고정할지(계열을 나중에 바꿔도 분모 불변), 지금처럼 매번 다시 계산할지(정확하지만 직관과 어긋날 수 있음). *(추천: 지금처럼 다시 계산한다 — 걸음 수를 고정하면 실제로 더 늘어난 세부 감정 화면들이 "안 세어지는" 진행 막대가 되어 더 혼란스럽다. 대신 걸음 수 글자("N / M")가 이미 분모 변화를 그대로 보여주므로 큰 문제로 보지 않는다.)* → **정함(D-099, 위임 판단)**: 매번 다시 계산한다(지금대로) — 고른 마음이 늘면 걸음도 느는 것이 사실이고, 단계 수 글자가 그 변화를 그대로 보여 준다.

## H. 배치·묶음

- 화면 맨 위, 뒤로가기·걸음 수(`.wf-count`)·⋯메뉴로 이뤄진 `.write-top`(sticky) 바로 아래.
- **진행 막대 자신은 sticky가 아니다** — `.write-top`만 스크롤에 고정되고 진행 막대는 본문과 함께 스크롤되어 사라진다(`write.css:4,9` 비교 — `.write-top`에만 `position:sticky`가 있다).
- 아래 여백 `space.3`(12px)로 안내 띠·본문과 구분.

## I. 문구

해당 없음 — 이 부품 자체에는 글자가 없다(걸음 수 글자는 별도 요소).

## J. 움직임

- 채움 폭 전환에 별도 `transition`이 없다 — 단계가 바뀌면 폭이 **즉시** 새 값으로 바뀐다(중간 애니메이션 없음, `write.css:10` 확인). 나타남·사라짐 연출도 없다.
- 움직임 줄이기와 무관 — 애초에 전환이 없어 추가로 끌 것도 없다.

## K. 접근성

- `role="progressbar"`, `aria-label="작성 진행"`, `aria-valuemin="1"`·`aria-valuemax="{전체 걸음 수}"`·`aria-valuenow="{현재 걸음}"`.
- F에서 확인했듯 이 값의 변화는 `aria-live`로 알려지지 않는다(K1 후보였으나 이미 F에 통합해 다뤘다).

## L. 화면 폭·기기

- 360~480: 폭 가득, 값은 % 계산이라 화면 폭과 무관하게 항상 정확한 비율로 보인다.
- 글자 확대 200%: 높이 3px 고정이라 글자 크기와 무관 — 영향 없음.

## M. 장면 위에서

- 세부 감정 화면(계열 300): 위 E1 참고 — 트랙 색이 계열에 맞춰 조정되지 않는다.
- 마음 고르기(초록 언덕): 트랙 배경만 `color-mix(ink 14%, transparent)`로 조정, 채움(ink)은 그대로.
- 그 밖(사건·이유·칭찬·감사·크기·편지): 흰 화면이라 기본값(E) 그대로.

## N. 하지 말 것·근거

- 진행이 줄어드는 것(뒤로 가기)을 막지 않는다 — 사용자가 이전 걸음으로 돌아가는 것은 정상적인 탐색이지 "실패"가 아니다.
- 근거: 이 부품은 별도 D-번호 결정 없이 시안 구현으로만 존재한다(§6에 절이 없었음, D-097 이관 대상).
