## 3. 바뀌는 전제

- **목표**: '본인이 매일 쓰기 시작' → **다른 사람이 가입해 쓰는 웹앱 공개**(U-9·U-11). 스토어는 그 뒤.
- **사용자 수**: 본인 1명(D-108) → 여러 명. 다행히 모든 행에 `owner_key`가 이미 있다(감리 REPORT §3.1 '공개 갈림길' — "지금 지킬 것은 '모든 행에 owner' 하나"). 바꿔야 하는 것은 로그인·세션의 주체를 만드는 쪽(`app/worker/src/context.ts`의 `OWNER_SUBJECT`·`OWNER_ALLOWLIST`, 접근 열쇠)이다.
- **시간 조건이 걸린 결정**(D-120 30일·D-121 60일·2주 뒤 돌아보기·A-7 첫 기록일 30일 문구): 실사용을 기다리지 않는다. AI는 첫 공개 뒤(U-14), 돌아보기는 지금(U-5).
- **비용**: D-019의 '추가 지출 0' → 작은 비용은 쓰기 전에 묻고 허용(U-16). 유료 AI API 금지는 AI가 없는 첫 공개에는 걸리지 않는다.
- **그대로인 것**: Worker 하나 + D1 구성, 저장 계약(하루 1편·revision·멱등), 내보내기·지우기·백업, 승인한 시안(`web/`)과 디자인 시스템, SERVICE_WHY의 원칙.
- **운영 건물 `emotion-diary-prod`**: 지우지 않는다(U-3). 공개 전까지 쓰는 사람이 없으니 구조를 바꾸기 가장 싼 때다 — 그래도 RK-045 규칙(바꾸기 전 내보내기 + 백업, 바꾼 뒤 복원 확인)은 지킨다.

**순서의 이유**
1. **돌아보기를 작성 흐름보다 먼저(2 → 3)**: 사용자가 가장 먼저 원한 것이다(U-5). 그리고 공학적으로도 유리하다 — 달력·통계는 읽기만 하는 화면이라 자판·자동 저장·충돌 같은 위험이 없어, 시안의 공통 부품(토큰·카드·하단 탐색·시트)을 위험이 낮은 곳에서 먼저 굳힐 수 있다. 지금의 평면 작성 흐름이 같은 데이터를 저장하므로 작성 흐름 이식을 기다릴 필요가 없다.
2. **평면으로 먼저 짓지 않고 처음부터 시안 모양으로**: 공개가 목표라 평면 화면은 결국 다시 짓는다. 시안은 2026-10-13에 전체 승인됐다(TASK-WEB-UI-02). 두 번 짓지 않는다.
3. **화면 도구 판정을 맨 앞(1)으로**: 감리 REPORT §5.3은 도구를 바꾸는 비용이 작성 흐름 이식 전 약 1,400줄 → 뒤 약 4,400줄로 커진다고 했다. 이제 시안 전체(약 4,500~4,900줄)와 달력·통계까지 옮기므로 미룰 이유가 없다.
4. **가입을 화면 이식 뒤(5)로**: 저장 표는 이미 사람별로 나뉘어 있어(`owner_key`) 로그인을 나중에 바꿔도 다시 짓는 것이 적다. 그리고 시안의 들어오는 길 화면이 곧 로그인 화면이라 함께 짓는 편이 한 번에 끝난다. 단, 통계를 서버에서 계산할지 기기에서 계산할지는 §5-3의 답에 따라 바뀌므로 통계 계산은 `app/shared/`의 순수 함수로 두어 어느 쪽에서든 돌게 짓는다.
5. **AI는 공개 뒤(8)**: U-14. AI가 꺼져 있어도 기록·돌아보기가 동작한다는 설계(D-120)는 그대로라 나중에 붙일 수 있다.
